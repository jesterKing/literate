Appendix H — Testing and verification reference

This appendix maps claims to the repository checks that can support them. The maintenance method is developed in Developing the book and program together, self-consistency in A generator that generates itself, and conservative failure policy in Resource bounds and fail-closed behavior.

No single command proves the whole system. Compilation, unit tests, generated-file comparison, fixed-point verification, package inspection, real-host acceptance, and human publication review answer different questions.

Test ownership: generated is not ordinary source

Most files under src/test/ are ordinary authoritative source and should be edited directly. Six test or acceptance files are exceptions: they are generated outputs owned by the literate book.

The generated test roots are:

  • src/test/headless/publication-headings.test.ts
  • src/test/headless/publication-settings.test.ts
  • src/test/headless/publication-highlight.test.ts
  • src/test/headless/publication-fonts.test.ts
  • src/test/headless/publication-screen.test.ts
  • src/test/acceptance/screen-host.js

Their root assembly is recorded in Appendix A — Program assembly maps, and their constituent fragments are collected later in this appendix. Edit those named fragments and regenerate; a direct edit to one of these six files will be overwritten.

All other test files are ordinary source unless and until a Literate output root says otherwise. This includes the remaining headless tests, src/test/headless/vscode-fixture.ts, src/test/headless/authoritative-book.ts, the remaining src/test/acceptance/ harnesses and evidence descriptions, and the VS Code test runner under src/test/suite/. Package metadata and test scripts are ordinary source as well.

Generated tests are still real tests: they compile, run, fail, and require independent expectations. Appendix H keeps test intent and generated test implementation together, while links lead back to the production policies they verify. Ordinary tests remain appropriate when a fixture or cross-cutting harness is clearer outside the book.

Suite organization

Headless regression tests

TypeScript headless tests live under src/test/headless/ and compile to out/test/headless/. They use Node's test runner and cover the engine, parser, CLI, transactions, editor adapters with a VS Code fixture, fragment symbols, browser presentation, publication, self-hosting, projections, direct language-server protocol, diagnostics, navigation, and code actions.

src/test/headless/vscode-fixture.ts supplies the mocked editor surface used by adapter tests. src/test/headless/authoritative-book.ts loads index.literate, all chapter sources, and the source template, then exposes fresh generation results to checks that compare projections or generated artifacts against the actual book.

Compile the TypeScript test tree without running it:

yarn test-compile

Run a focused compiled group after that command, for example:

node --test out/test/headless/language-*.test.js \
  out/test/headless/extension-adapter.test.js \
  out/test/headless/editor-symbols.test.js \
  out/test/headless/code-actions.test.js

A focused command is useful while iterating, but it does not include lint, generated-file comparison, unrelated headless suites, packaging, or real hosts.

Complete default suite

The default repository suite is:

yarn test

Its script builds the publication Mermaid worker, compiles the project, lints TypeScript, runs every compiled out/test/headless/*.test.js, and finally runs the CLI generated-file check. It therefore detects stale generated source or HTML, but it does not perform self-host fixed-point verification, package a VSIX, run real editor UI, invoke every publication acceptance harness, or judge rendered pages.

VS Code extension-host suite

Run the extension test entry with:

yarn test:extension

This builds the TypeScript and bundled extension, then invokes the VS Code test runner. The host runner may download its configured VS Code test host and requires a suitable graphical environment. Its sample/integration coverage supplements rather than replaces the headless suite and interactive smoke testing.

Publication acceptance scripts

The package scripts expose focused real-tool routes:

Generated-file verification

Use either command to compare the complete current generation plan with disk without writing outputs:

yarn literate check
yarn check:generated

A valid check compares every planned source and HTML destination as current, missing, or stale. It does not detect or delete orphaned files left behind by a removed or renamed root. Inventory review is required for that case.

For a read-only command invocation that must not rebuild the CLI wrapper first, use a known existing executable:

node out/cli-entry.js check

The direct command reads saved disk inputs. It does not see unsaved editor buffers. Do not run CLI generation concurrently with editor generation against the same project.

Fixed-point verification

The fixed-point route is:

yarn check:self

Equivalently, yarn literate self-check names the underlying CLI command. It first requires all planned outputs to match disk. It then:

  1. generates a fresh complete plan from the captured book;
  2. overlays fresh generated TypeScript in memory over ordinary checkout sources;
  3. type-checks that combined program without replacing project files;
  4. bundles the fresh engine and runs it in a bounded child process;
  5. requires the child to return a well-formed plan without diagnostics; and
  6. compares destination sets and exact content, independent of array order.

If S is the captured snapshot, P is its fresh plan, and E is the engine built from that plan, the verified condition is:

E(S) = P

This proves that fresh generated sources type-check in context and that the fresh engine reproduces the complete plan from which it was built. It does not prove CLI reporting, transaction recovery, editor behavior, publication quality, external-tool compatibility, or safety of the project code it executes. Run it only for trusted self-hosting source.

Package verification

A build-directory test does not establish archive contents. After:

yarn package:vsix

inspect the actual out/<name>-<version>.vsix. The opt-in src/test/acceptance/publication-package.mjs harness can consume existing runtime bundles or an explicit existing VSIX. It checks the runtime allowlist, byte identity between archive and reviewed bundles, dependency-graph closure, publication-only request boundaries, snapshot publication, portable resources, and isolated helper execution. It does not build, generate, install, or download its prerequisites.

Package closure is not a complete transitive license audit. Review THIRD_PARTY_NOTICES.md, manifest declarations, and portable resource licenses separately.

Verification routes by change

Use these as starting points, then add the affected subsystem's focused tests.

Prose-only chapter change

node out/cli-entry.js check

After deliberate regeneration, require no unexpected generated program-source diff. Review generated HTML, links, headings, diagrams, and publication order where the prose move changes structure.

Fragment implementation change

yarn literate generate
yarn test
yarn esbuild

Review generated source before testing. Add a focused test near the changed invariant. If the engine or generator changed, also run yarn check:self.

CLI or transaction change

Run the focused CLI and transaction tests, then yarn test. Exercise both human and --json output when the response contract changes. Use fault-injection cases for preflight, rollback, recovery, and committed cleanup.

Editor integration change

Run the focused headless adapter tests, yarn test, and yarn esbuild. Add extension host or interactive evidence when behavior depends on real workspace trust, commands, preview, completion widgets, editor buffers, filesystem providers, or cancellation UI.

Language-service change

Compile, run the focused language-*.test.js group, then the full suite. Use the appropriate installed-server or UI harness for claims about real protocol compatibility or visible editor behavior. Confirm that requests do not materialize generated files.

Publication change

Run the focused headless publication suites and the corresponding acceptance script. A format or renderer change may require real Pandoc, browser, font, or TeX evidence. Inspect warnings and pages; successful PDF compilation is not a typography review.

Packaging or release change

Build all shipped entry points, run the full suite and relevant fixed-point checks, create a VSIX, inspect its entries, and run package or installed-host acceptance for changed surfaces. Test the exact archive intended for publication.

Supported environments and known limits

  • Headless tests require no graphical editor, but some focused publication tests use injected adapters and therefore do not prove real tool compatibility.
  • The extension-host route needs a suitable VS Code host and display and may acquire its configured test host.
  • Direct language-server acceptance requires explicitly installed server executables; it neither installs servers nor proves universal LSP compatibility.
  • Real publication acceptance requires the external tools appropriate to the tested route. Mermaid needs an explicit browser; PDF needs the supported TeX process model.
  • Editor-driven process ownership is restricted to trusted local file workspaces; remote, web, and virtual environments retain only the capabilities their adapters can support safely.
  • Filesystem tests establish recoverable exception behavior, not crash durability, simultaneous multi-file visibility, or protection from external concurrent writers.
  • Deterministic engine plans do not imply byte-identical PDF or diagram output across external toolchains and fonts.
  • Resource bounds fail closed at their defined boundaries but do not prove a universal CPU, memory, disk, or filesystem-latency limit.

Report validation in terms of the command actually run and the claim it supports. “The headless suite passed,” “the fixed point passed,” “the VSIX was inspected,” and “the PDF was reviewed” are complementary statements, not interchangeable ones.

function blocks(document: PandocDocument): PandocBlock[] {
    const result: PandocBlock[] = [];
    function visit(block: PandocBlock): void {
        result.push(block);
        if (block.t === 'Div') { block.c[1].forEach(visit); }
        if (block.t === 'BlockQuote') { block.c.forEach(visit); }
        if (block.t === 'BulletList') { block.c.forEach(item => item.forEach(visit)); }
        if (block.t === 'OrderedList') { block.c[1].forEach(item => item.forEach(visit)); }
    }
    document.blocks.forEach(visit);
    return result;
}

<<publication heading test helpers>>=
function target(slug: string, path = 'index.literate'): string {
    const hex = (value: string) => value.split('').map(c => c.charCodeAt(0).toString(16).padStart(4, '0')).join('');
    return 'h-' + hex(path) + '-' + hex(slug);
}
function prepare(sources: SourceDocument[]): PandocDocument {
    const project = parseProject(sources), before = JSON.stringify(project);
    const result = preparePandoc(project, () => [{ t: 'Para', c: [{ t: 'Str', c: 'CONTRIBUTION' }] }]);
    assert.deepEqual(result.diagnostics, []);
    assert.equal(JSON.stringify(project), before);
    assert.ok(result.document);
    return result.document;
}
function headingIds(document: PandocDocument): string[] {
    return blocks(document).flatMap(block => block.t === 'Header' ? [block.c[1][0]] : []);
}
function destinations(document: PandocDocument): string[] {
    return blocks(document).flatMap(block => block.t === 'Para' || block.t === 'Plain'
        ? block.c.flatMap(inline => inline.t === 'Link' ? [inline.c[2][0]] : []) : []);
}

async function preview(inputs = documents(), f = fixture()) {
    for (const doc of inputs) { f.workspace.textDocuments.push(f.document(doc.path, doc.text)); }
    const subscriptions: vscode.Disposable[] = [];
    const api = await f.extension.activate({ subscriptions } as unknown as vscode.ExtensionContext);
    const md = new MarkdownIt({ highlight: (code, language) =>
        hljs.getLanguage(language) ? hljs.highlight(code, { language }).value : '' });
    const delegated: { index: number; token: Token }[] = [];
    const original = md.renderer.rules.fence!;
    md.renderer.rules.fence = (tokens, index, options, env, renderer) => {
        delegated.push({ index, token: tokens[index] });
        return original(tokens, index, options, env, renderer);
    };
    api.extendMarkdownIt(md);
    md.core.ruler.push('host_source_map', state => {
        for (const token of state.tokens) {
            if (token.map && token.type !== 'inline') {
                token.attrSet('data-line', String(token.map[0]));
                token.attrJoin('class', 'code-line');
            }
        }
    });
    const repository = subscriptions.find(value => value instanceof f.extension.FragmentRepository) as
        InstanceType<typeof f.extension.FragmentRepository>;
    for (const doc of inputs.length ? inputs : documents()) {
        md.render(doc.text, { currentDocument: f.document(doc.path, doc.text).uri });
    }
    await tick();
    await new Promise<void>(resolve => setTimeout(resolve, 5));
    return { md, delegated, f, repository, dispose: () => subscriptions.forEach(value => value.dispose()) };
