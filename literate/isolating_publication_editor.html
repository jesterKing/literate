Isolating publication from the editor

Publishing from an editor is convenient, but the editor process is the wrong place to host Pandoc, a browser, TeX, and long-running filesystem transactions. A stuck converter could make editing unresponsive. A large dependency graph would enlarge the extension's trusted runtime. Cancellation could interrupt a write at exactly the wrong moment.

Literate keeps the editor adapter small. It owns user prompts, workspace authority, a fresh source snapshot, and a bounded request to an external helper. The helper owns publication orchestration and returns one structured result after its output transaction has settled.

    Adapter-->>Reader: Report output and warnings

The arrows show authority handoff. The helper receives a snapshot and explicit arguments, not access to editor APIs. The diagram omits cancellation signals, which flow from the adapter to the helper and then through each active process adapter.

Establish authority before convenience

Publication is limited to a trusted local desktop workspace backed by ordinary files. Remote and web workspaces are rejected. The selected workspace folder must still belong to the current workspace at each asynchronous boundary.

The project root is resolved canonically and must be a real directory rather than a symbolic-link alias. Source, manifest, and destination paths are checked for root containment and safe components. A save dialog suggests a location but does not establish authority; the returned URI is independently checked for local-file scheme, extension, and containment.

If the selected workspace folder is removed while publication is active, authority is revoked and cancellation is latched. Re-adding an equal-looking folder does not restore the old operation's authority.

Executables are explicit user choices

The helper runs under an external Node executable, never the editor's embedded Electron process. The path is absolute and comes only from user-level settings, not from workspace-controlled configuration. An optional Chromium path follows the same rule.

This distinction prevents a project from silently selecting an executable merely by changing workspace settings. Pandoc and TeX remain system dependencies checked by the helper's normal preflight. The editor does not download tools or alter the user's installation.

A font manifest is different: it is a root-relative project input and may be chosen for the workspace. Its path still crosses the same containment and symlink checks as other publication resources.

Capture one fresh source snapshot

Publication should include unsaved literate text without forcing a save-all. The adapter first clones every eligible open buffer synchronously. Empty and newly created file-backed buffers override disk just like nonempty buffers. Untitled, foreign-scheme, and out-of-root documents do not enter the snapshot.

Only after overlays are captured does the adapter traverse disk. Discovery is sorted and excludes generated, dependency, and editor-test directories according to the shared project policy. A disk file with an open overlay is not read a second time.

flowchart TD
    Open[Eligible open buffers] --> Clone[Clone text before awaiting disk]

    Disk[Sorted project discovery] --> Choose{Overlay for path?}
    Overlay --> Choose
    Choose -->|Yes| Buffer[Use cloned buffer]
    Choose -->|No| Saved[Read bounded saved file]

The arrows show precedence, not a merge of two texts. Every path contributes one captured value. The diagram omits binary assets and fonts because they remain on disk and are checked later by the helper.

The adapter accounts for serialized request bytes while collecting documents and checks the final envelope again. Individual disk files are size-checked before reading. This bounds memory before the helper applies its independent input bound.

Serialize publication with other writers

A global publication guard rejects overlapping publication commands. A repository queue, when supplied, serializes snapshot capture and the helper's complete lifetime with ordinary generation.

Prompts occur before acquiring that queue, so a user deciding on paper or a filename does not block unrelated work. Once acquired, the queue remains held until the helper closes and its result is validated. A cancellation request does not release the queue early while rollback may still be running.

This ordering gives the source snapshot and output transaction one operation boundary. It does not claim to prevent unrelated external programs from changing the workspace concurrently.

One request, one helper lifetime

The helper is a one-request process. Standard input carries one JSON envelope terminated by end-of-file. It admits only LaTeX and PDF publication commands in structured-output mode; help, self-hosting, and unrelated command surfaces are not available.

Input is counted as it arrives and has both a byte bound and a delivery deadline. The helper validates the envelope before lazily loading the shared publication runner. It writes no readiness chatter, so standard output remains a single machine-readable result.

The implementation packages this boundary as publication-helper.cjs. The editor spawns it with an argument vector and shell: false, sends the captured documents, and closes standard input. The working directory is the canonical project root, but the request still carries explicit safe relative destinations.

Runtime bundles preserve the boundary

An installed extension carries three publication runtime artifacts:

  • the external helper that owns one publication request;
  • the browser worker that owns diagram rendering and Chromium; and
  • the offline Mermaid program loaded by that worker.

Each artifact is built as a closed runtime graph. Unresolved package imports, source toolchains, browser installers, and accidental development dependencies are rejected at build time. The browser artifact has no Node imports. The helper does not expose self-host verification or source-generation entry points that publication does not need.

These bundles make installation independent of a development checkout while preserving isolation. They do not bundle Pandoc, TeX, or Chromium, and they never download those tools at runtime.

Cancellation is graceful at the transaction boundary

The adapter forwards editor cancellation by sending a termination signal to the helper. The helper latches cancellation before reading input and keeps signal listeners through the shared runner's completion. Browser rendering and PDF compilation own process groups because their tools may create descendants. The Pandoc adapter owns and terminates its direct child only.

The editor deliberately has no automatic hard-kill fallback for the helper. Killing it during rollback could abandon staged files or backups. If graceful termination is slow, the adapter reports that it is waiting and keeps the publication lock until process close.

stateDiagram-v2
    [*] --> Active
    Active --> Cancelling: user cancels or authority is revoked
    Cancelling --> Cleaning: helper acknowledges and unwinds
    Active --> Cleaning: operation completes
    Cleaning --> Closed: process closes and pipes drain
    Closed --> [*]

The lock follows the helper through Cleaning; it is not released at the cancellation request. The diagram intentionally has no forced-termination shortcut. Subprocess adapters may terminate their owned process groups, but the transaction coordinator must be allowed to finish its recovery work.

Trust the result only after protocol validation

Combined standard output and error are bounded. An execution deadline requests helper cancellation, but it does not impose a hard upper bound on graceful cleanup. The editor may report that cleanup is taking unusually long and continues waiting for process close—not mere exit—because inherited pipes may still be draining and a transaction may still be restoring files.

A zero exit status is necessary but not sufficient. The adapter parses the structured response, checks that it describes the requested command, and requires the selected destination to be reported as either newly written or already current. Warnings are then displayed separately from errors.

Cancellation does not overwrite an already committed truth. If cancellation arrives after the helper has committed and the validated response reports success, the output is complete. If workspace authority was revoked after commit, the adapter reports the completed path but does not remember settings, offer an open action, or open the file.

Prompts do not become hidden state

Paper, four margins, and destination are always explicit prompts. The previous successful choices provide defaults for the same canonical root and output kind; they do not bypass validation or the prompt itself. Canceling any prompt ends the operation before a helper is spawned.

Margin validation checks both each side and the resulting body dimensions. The renderer validates geometry again because UI checks are convenience, not a trust boundary.

After a validated success, the editor offers Open Output. Only when the user chooses it is a PDF opened through the editor's general file-open command rather than as a text document. LaTeX and PDF destinations remain inside the selected project so the helper's transaction and input-protection rules apply.

Isolation keeps responsibilities honest

The editor knows about workspace trust, open buffers, prompts, progress, and user cancellation. The helper knows about publication semantics, resources, converters, compilers, and transactional writes. External tools receive explicit arguments and bounded protocol streams, but they remain trusted processes with the filesystem authority inherited from the helper. Project resources are policy-checked; not every resource class has a byte quota. Pandoc owns one direct-child lifetime; the browser and PDF adapters own process-group lifetimes.

No boundary is a complete sandbox. The external helper has project access, TeX is a trusted compiler, and filesystem races with unrelated programs remain possible. The design nevertheless prevents editor APIs, unsaved source capture, subprocess ownership, and output commitment from collapsing into one unreviewable lifetime.

Publication therefore ends where it began: one captured literate project is interpreted once, then carried through explicit adapters whose authority and failure semantics match the medium they serve.
