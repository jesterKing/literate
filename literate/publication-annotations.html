Shared publication annotations

Some explanations need a little more than the main flow of prose. A term may need a reusable definition, while a note may deserve space beside the page instead of interrupting the paragraph. Literate records both forms as annotations in the book and lets each renderer decide how best to present them.

flowchart TD
    Prose[Prose and annotation fences] --> Collect[Collect terms, notes, and uses]
    Collect --> Resolve[Resolve stable identities and references]
    Resolve --> Shared[Renderer-neutral annotation model]
    Shared --> Screen[Preview and generated HTML]
    Shared --> Print[LaTeX notes and indexes]

The shared model deliberately stops before presentation. It says which terms and notes exist, where they came from, and how references resolve; it does not decide whether a note becomes a side rail, a panel, a link, or an index entry. That separation lets screen and print disagree about appearance without disagreeing about meaning.

Annotations are prose-local fenced blocks, not contributions to generated program fragments. A TERM header names a reusable concept and gives it a display title; a NOTE header takes no arguments. TERM bodies remain part of the source prose, while NOTE bodies are available to the publication rail. Headers are case-sensitive, and Markdown-it determines their fence boundaries, including the behavior of an unclosed fence.

The exact accepted grammar is intentionally narrow. A term header has the form TERM key "Display title". Keys begin with an ASCII letter and may continue with letters, digits, _, ., :, or -, up to one hundred characters. The title is a required JSON string of at most two hundred Unicode code points. These limits make identities predictable before any renderer sees them. The mechanical root that assembles the annotation module is in the program assembly appendix.

Renderer-neutral contract

Locations use zero-based source lines and UTF-16 columns. Document uses point to the enclosing inline block; body uses point to the enclosing annotation fence. A use's tokenIndex selects an inline token in the document tokens or in parseAnnotationBody(owner.body); childIndex selects that token's link_open child. This intentionally does not claim character-exact Markdown link locations. Definition tokenIndex selects the original fence. Owners are document paths for ordinary prose and annotation targets for body prose. Lists and headings in ordinary prose are included. Inline code, code blocks, and images are not uses.

<<annotation contracts>>=
import MarkdownIt = require('markdown-it');
import Token = require('markdown-it/lib/token');
import type { GenerationDiagnostic as Diagnostic } from './engine';

type Location = { path: string; line: number; column: number };
export interface PublicationTerm {
    key: string; title: string; target: string; at: Location; tokenIndex: number; body: string;
}
export interface PublicationNote {
    target: string; number: number; at: Location; tokenIndex: number; body: string;
}
export interface PublicationTermUse {
    key: string; target?: string; at: Location; owner: string;
    tokenIndex: number; childIndex: number;
    resolution: 'resolved' | 'missing' | 'ambiguous';
}
export interface PublicationAnnotations {
    terms: PublicationTerm[]; notes: PublicationNote[];
    uses: PublicationTermUse[]; diagnostics: Diagnostic[];
}

One deterministic body parser

Bodies allow paragraphs, ordered and unordered lists, emphasis, strong emphasis, inline code, links, text and line breaks. All other token kinds are rejected, including headings, blockquotes, tables, strikethrough, images, indented code, code fences (including nested TERM/NOTE and Mermaid), and raw HTML. HTML parsing is enabled only to recognize and diagnose HTML, not to authorize rendering it. Escaped HTML and HTML inside inline code remain ordinary text/code. The parser returns tokens even for invalid bodies; the collector validates those same tokens. Adapters must honor diagnostics and never render rejected HTML unsanitized.

<<annotation body parsing>>=
export function parseAnnotationBody(body: string): Token[] {
    return new MarkdownIt({ html: true }).parse(body, {});
}
const allowedBodyTokens = new Set([
    'paragraph_open', 'paragraph_close', 'inline', 'text', 'softbreak', 'hardbreak',
    'bullet_list_open', 'bullet_list_close', 'ordered_list_open', 'ordered_list_close',
    'list_item_open', 'list_item_close', 'em_open', 'em_close', 'strong_open',
    'strong_close', 'code_inline', 'link_open', 'link_close'
]);
function invalidBodyToken(tokens: readonly Token[]): Token | undefined {
    for (const token of tokens) {
        if (!allowedBodyTokens.has(token.type)) { return token; }
        const invalid = invalidBodyToken(token.children || []);
        if (invalid) { return invalid; }
    }
    return undefined;
}

Stable identities and safe lookup

Targets have distinct generated namespaces and hex-encoded UTF-16 components, never author-controlled raw identifiers. TERM targets derive from the key; duplicate definitions receive location suffixes so preview targets remain unique. NOTE targets derive from path and fence line/column, not the encounter number. Numbers are one-based in caller document/fence order. Keys are case-sensitive. Percent-encoded term destinations are decoded exactly once; malformed encodings and invalid keys cannot resolve. Missing and ambiguous links return undefined, never the original href. termByTarget likewise returns undefined for unknown IDs.

Annotation identity is presented in Shared annotations and identities.

Collection before resolution

Collection is pure with respect to caller tokens. Invalid headers produce no annotation; valid headers retain their bodies even when body validation fails. Every duplicate definition is diagnosed and all uses of that key are ambiguous. Forward and cross-document uses resolve after collection. Unknown or malformed term destinations are missing uses and diagnostic, so strict adapters can reject them while previews retain occurrence metadata. Diagnostics have stable codes.

Markdown-it emits list bodies as a flat block-token stream with inline children. Iterating every inline token handles arbitrary list nesting without inventing indexes or scanning raw Markdown. Image alt children are deliberately excluded.

<<annotation inline collection>>=
    const collectUses = (tokens: readonly Token[], owner: string,
        location: (token: Token) => Location, tokenOffset = 0): void => {
        tokens.forEach((token, tokenIndex) => {
            if (token.type !== 'inline') { return; }
            (token.children || []).forEach((child, childIndex) => {
                const href = child.type === 'link_open' ? child.attrGet('href') : null;
                if (!href?.startsWith('term:')) { return; }
                result.uses.push({ key: termKey(href) ?? href.slice(5), at: location(token),
                    owner, tokenIndex: tokenIndex + tokenOffset, childIndex, resolution: 'missing' });
            });
        });
    };

Required titles are parsed as JSON, rather than unescaping with a second grammar. Duplicate target suffixes are assigned after all definitions are known; body use owners are updated together with the corresponding target.

The temporary location-qualified term targets distinguish duplicate body owners. Unique terms shed that suffix, giving references an identity stable across prose edits and document moves. Duplicate definitions remain individually addressable, but never become a successful key resolution.

<<annotation final resolution>>=
    const byKey = new Map<string, PublicationTerm[]>();
    for (const term of result.terms) { byKey.set(term.key, [...(byKey.get(term.key) || []), term]); }
    for (const term of result.terms) {
        if (byKey.get(term.key)!.length > 1) {
            report(term.at, 'annotation-duplicate', `Duplicate TERM key: ${term.key}`);
        } else {
            const target = `annotation-term-${encode(term.key)}`;
            for (const use of result.uses) { if (use.owner === term.target) { use.owner = target; } }
            term.target = target;
        }
    }
    for (const use of result.uses) {
        const terms = keyPattern.test(use.key) ? byKey.get(use.key) || [] : [];
        use.resolution = terms.length === 1 ? 'resolved' : terms.length > 1 ? 'ambiguous' : 'missing';
        if (use.resolution === 'resolved') { use.target = terms[0].target; }
        else { report(use.at, `annotation-${use.resolution}`, `${use.resolution} TERM use: ${use.key}`); }
