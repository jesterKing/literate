Exploring the fragment graph

A source file offers one linear order. A literate program has at least two: the narrative order of chapters and the dependency order in which fragments include one another. Following a single definition link answers “where does this name begin?” It does not answer “what does this fragment depend on?” or “how much of the program is hidden behind this reference?”

Graph exploration makes those relationships visible without expanding the program into a second source editor. Literate offers two complementary views: a workspace tree for surveying families and an inline disclosure beside a reference in the rendered explanation.

A dependency graph is not a folder hierarchy

Each fragment family is a node. A reference in one family's contributions creates a directed edge to another family. Several parents may point to the same child, a parent may mention the same child more than once, and invalid projects may contain a cycle. None of these relationships has a unique “correct” tree position.

flowchart TD
    Entry[Entry family] --> Parse[Parse request]
    Entry --> Validate[Validate request]
    Parse --> Shared[Shared error model]
    Validate --> Shared
    Shared --> Format[Format response]
    Format --> Validate

The arrows mean “contains a reference to,” not “owns.” Shared error model therefore appears once as a graph node even though two parents use it. The final edge illustrates a cycle: unfolding the graph as if it were an ordinary directory tree would never finish. The names are illustrative concepts, not declarations in the book.

An explorer must consequently choose a viewpoint. The workspace tree shows the same family under each parent from which it is reached. Inline exploration starts at one particular reference. Repetition is informative in both views because it preserves context; global deduplication would hide why a dependency is present.

The workspace tree surveys project families

At the top level, each workspace folder forms an independent branch. Beneath it, the view lists accepted fragment families in deterministic project order. A family can be opened to reveal the direct references found in its unexpanded authored code. Selecting a resolved item opens the first accepted contribution for that family. An unresolved child remains visible as a broken edge but has no invented navigation destination.

The view asks for children only when the editor expands an item. VS Code calls this contract a TreeDataProvider, and each visible row is a TreeItem. FragmentExplorer and FragmentNodeProvider are the adapter classes that translate the repository's family map into that contract.

sequenceDiagram
    participant Reader
    participant View as Fragment tree
    participant Provider as Tree data provider
    participant Repo as Project repository

    Reader->>View: Expand workspace folder
    View->>Provider: Request root children
    Provider->>Repo: Read accepted families for this workspace
    Repo-->>Provider: Ordered family map
    Provider-->>View: One item per family
    Reader->>View: Expand a family item
    View->>Provider: Request this item's children
    Provider->>Repo: Read unexpanded family text
    Provider-->>View: Direct resolved and unresolved references

The arrows are demand-driven editor calls. The provider does not recursively build the entire graph when the view appears. The diagram omits refresh notifications: when project text changes, the provider invalidates the tree and the editor requests visible children again.

The current tree mirrors edges rather than proving a finite unfolding. A cycle can therefore cause the same family names to reappear as a reader repeatedly expands the cycle. Lazy requests prevent one expansion from recursively constructing everything, but the tree does not currently add cycle markers or a view-wide expansion budget. This is an important limit: the tree is a convenient survey, not the bounded browser used for inline expansion.

Inline exploration stays beside the explanation

In generated HTML and editor preview, an accepted reference can gain a disclosure control. Opening it shows the referenced family's ordered contributions, preserving its code segments and adding controls to references inside those contributions. A reader can explore several layers without leaving the paragraph or fragment that raised the question.

This view is optional progressive enhancement. Ordinary semantic links exist before the browser program runs. If scripts are unavailable, the links still navigate. If an exploration payload is too large or a requested panel exceeds its budget, the baseline explanation remains intact.

The renderer embeds an inert model derived from the publication snapshot. Each contribution is stored once as text and reference segments; families point to their ordered contribution identities. Browser code creates panels only when requested. It never reparses source or scans highlighted HTML to infer dependencies.

flowchart TD
    Model[Accepted publication model] --> Serialize[Build inert bounded payload]
    Serialize --> Baseline[Render ordinary semantic links]
    Baseline --> Control[Add disclosure for an explorable reference]
    Control --> Request[Reader opens one family]
    Request --> Preflight[Plan complete panel and charge its costs]
    Preflight --> Fits{Within depth, panel, part, segment, and byte budgets?}
    Fits -->|No| Refuse[Keep the baseline link and show no partial code]
    Fits -->|Yes| Commit[Create the complete panel]
    Commit --> Nested[Nested references may offer another disclosure]

The arrows show two separate safety gates. Payload serialization must fit before the browser receives the model. A later panel must also fit before any candidate nodes are attached. The diagram omits styling and syntax highlighting so the all-or-nothing resource decision remains clear.

Bounds preserve meaning

A valid graph can still expand into an impractical amount of screen content. A small cycle is the clearest example, but a broad acyclic graph can be just as expensive. The browser therefore enforces independent limits on nesting depth, retained panels, visited contributions, reference segments, serialized payload, and escaped text bytes.

These are semantic safety limits for the view, not pagination hints. If a requested panel does not fit, Literate refuses that whole panel. Truncating halfway could make a family appear complete while silently omitting a later contribution or reference. The ordinary link remains the reliable fallback.

Costs belong to private browser state, not editable DOM attributes. Collapsing a panel recursively destroys its descendants and releases their charged resources. If content is detached or the payload changes, reconciliation performs the same cleanup. This makes the budget describe live exploration rather than every panel a reader has ever opened.

stateDiagram-v2
    [*] --> Collapsed
    Collapsed --> Planned: reader requests expansion
    Planned --> Expanded: complete plan fits all budgets
    Planned --> Collapsed: request is unsafe or too large
    Expanded --> Expanded: open a bounded child panel
    Expanded --> Collapsed: collapse, detach, or model change
    Collapsed --> [*]: root removed

This state machine describes one disclosure and its owned descendants. Returning to Collapsed releases child panels before the parent charge. It intentionally omits the separate payload-validation state, which occurs before any disclosure becomes available.

Cycles become finite paths through a view

The semantic graph may contain a cycle even though generation will reject expanding it. Exploration must still remain safe while an author is diagnosing the project. The browser does not try to make the graph acyclic or silently drop the repeated edge. Instead, each click extends one visible path until the depth or resource policy refuses another panel.

This is a useful distinction:

  • graph validation answers whether complete source expansion is legal;
  • exploration answers how much of a dependency neighborhood can be shown safely;
  • navigation answers where a selected accepted identity currently lives.

A cycle may therefore be inspectable even though it is not generatable. The view remains finite because display work is bounded independently from graph validity.

Links retain host authority

Exploration data can name logical targets, but it cannot grant arbitrary navigation. For standalone HTML, links must match safe local chapter-and-anchor shapes. In editor preview, a target uses the same temporary host capability as ordinary semantic links. The browser accepts a host-provided baseline destination only when it matches the requested target and an allowed shape.

A destination inside the inert payload does not become trusted merely because the renderer serialized it. Native editor capabilities retain their opaque host routing data, while arbitrary schemes, changed targets, fragments on native capabilities, and malformed paths remain text. HTTPS is accepted only when it comes from a matching baseline link already supplied by the host, not from payload metadata alone.

This separation keeps the browser client portable. It knows how to validate and present a destination, but only the editor adapter can decide that a trusted, currently present workspace may open a source document.

Focus and disclosure are part of correctness

An inline graph is not useful if opening it loses keyboard position or closing it leaves focus in removed content. Each disclosure is a real button with expanded state and a controlled panel. When teardown removes the focused panel, focus returns to a surviving top-level disclosure or baseline anchor.

Text enters the panel through text nodes rather than interpreted markup. Nested controls are created only for validated reference segments. These choices make the view usable with a keyboard and prevent source text from becoming browser structure. Accessibility is not an extra rendering mode; it follows from treating exploration as navigation rather than decoration.

Two views, one model, honest limits

The workspace tree is good for answering “what families are in this project?” and “what does this family directly reference?” Inline exploration is good for answering “what lies behind this reference while I continue reading here?” They should continue to share family identity and repository snapshots while keeping their different lifetimes and budgets explicit.

Future improvements to the tree could mark active-path cycles, distinguish repeated edges, and adopt bounded expansion accounting like the browser. Those changes should refine presentation rather than introduce another fragment parser. The extension's public surface already has a natural place for such evolution: declarative view and command contributions joined to activation-owned adapters. The next chapter explains that boundary.
