One generator, several hosts

The complete generation plan from the previous chapter exists in memory. Nothing has been written, no editor has been updated, and no terminal has printed a result. Those effects belong to a host: the environment that captures inputs, asks the shared semantic core a question, and decides what to do with the answer.

Literate has several hosts because writing a file is only one way to use a literate project. A command can inspect its structure. An editor can work from unsaved text. A preview can render the explanation. A publication tool can prepare a book. A language service can project fragments into the source seen by another programming tool. These products differ, but they must not acquire different meanings for the same fragment language.

One semantic center, several boundaries

The phrase “one generator” does not mean that every consumer calls one enormous function. It means that project identity, ordering, fragment syntax, graph rules, source locations, path policy, and deterministic expansion have one semantic center. Specialized consumers take narrower views of the same captured project.

flowchart TD
    Snapshot[Captured project snapshot] --> Core[Shared semantic core]
    Core --> Plan[Complete output plan]
    Core --> Model[Parsed publication model]
    Core --> Projection[Mapped source projection]
    Plan --> CLI[Command line]
    Plan --> Editor[Editor repository]
    Model --> Preview[Live preview]
    Model --> Book[Print publication]
    Projection --> Language[Language service]

The arrows from the core mean “derive under shared rules.” The later arrows mean “adapt a result to one environment.” The diagram intentionally omits filesystem, editor, browser, and subprocess details. Those details vary by host; the meaning of a project must not.

This separation prevents a particularly troublesome kind of defect. If the editor recognized a fragment that the command line rejected, an author could see a valid project while editing and a broken project when checking it elsewhere. Shared semantics turn that disagreement into an architectural error rather than an accepted feature.

A host captures reality

Pure interpretation begins only after a host has turned its surroundings into explicit values. The command line discovers saved documents on disk. The editor combines discovered files with open buffers, including unsaved and empty buffers. A publication request may receive a complete snapshot from an editor so that the book being exported matches what the author can see.

The capture rule is simple but strict: one path contributes one complete text to one operation. A host must not read half a document, wait for an edit, and then read the other half. If its inputs change, it captures another snapshot and starts new work or discards the stale result.

sequenceDiagram
    participant World as Host environment
    participant Host
    participant Core as Semantic core

    World->>Host: Files, buffers, settings
    Host->>Host: Capture one snapshot
    Host->>Core: Explicit documents and templates
    Core-->>Host: Model, diagnostics, or plan
    Host->>Host: Check result is still current
    Host-->>World: Report, render, or commit

The return arrow does not grant permission to perform every effect. A diagnostic may require reporting and forbid output commitment. A stale result may be valid for its captured snapshot but no longer valid for the editor state that would receive it. Validity and freshness are related checks, not the same check.

Generation hosts decide whether to write

The command-line and editor adapters can both consume a complete output plan. They share the rule that diagnostics prevent writes, and they share the transaction protocol used to change several outputs safely. They differ in their surroundings.

The command line reads saved inputs, runs one requested operation, reports a result, and exits. It is well suited to repeatable checks and automation. The editor lives longer. It observes workspace and buffer changes, serializes refreshes, replaces diagnostics for the affected workspace, and queues a later pass when inputs change during earlier work. Callers that expose version-sensitive results perform their own freshness checks.

Neither adapter is a second generator. In particular, neither should repair an invalid fragment graph, choose a different document order, or recreate expansion with host-specific string replacement. Their authority begins at acquisition and resumes at effects; project meaning remains in the core.

Read-only and writing operations also need a visible boundary. Navigation or completion may require a fresh parsed model without any reason to touch generated files. A check may compare a complete plan with disk without changing it. Generation adds commitment only after the same planning and validation have succeeded.

flowchart TD
    Result[Semantic result] --> Valid{Diagnostics empty?}
    Valid -->|No| Explain[Publish diagnostics]
    Valid -->|Yes| Intent{What did the caller request?}
    Intent -->|Inspect| Describe[Describe project structure]
    Intent -->|Check| Compare[Compare with external state]
    Intent -->|Preview| Render[Render without output writes]
    Intent -->|Generate| Commit[Commit changed outputs]

The branches describe host intent, not separate interpretations of the source. That distinction matters when a tool grows: adding a convenient command should not add another fragment language by accident.

Preview is presentation, not generation

A preview answers, “How does this explanation look now?” It may use the current buffer before the document is saved. It renders Markdown, contribution boundaries, links, annotations, diagrams, and theme choices for a screen. It does not need to write the tangled program or the generated book merely to answer that question.

Preview still depends on shared identities. A contribution link must refer to the same logical contribution that publication and navigation recognize. A theme must come from the same root setting. Invalid source must not gain authoritative semantic links simply because a renderer can display its Markdown.

Keeping preview separate from output commitment has a practical benefit for every reader, not only programmers: looking at a document cannot unexpectedly rewrite a project. Presentation remains a read-only interpretation until an explicit host operation requests something stronger.

Publication is another view of the captured project

Screen and print publication need the ordered prose, Markdown structure, stable identities, annotations, and contribution content. They do not need to pretend that a generated source file is the book. A publication pipeline therefore starts from the parsed project model and builds a renderer-neutral document before a specific screen or print renderer takes over.

Publication can impose additional policy. A print bridge may reject a Markdown construct it cannot represent faithfully. An image collector may enforce path and size limits. Such checks narrow what a particular product can accept; they do not change what a fragment declaration means.

External tools, when explicitly selected, remain outside the semantic core. The host controls their arguments, working directories, time limits, output bounds, and cancellation. This keeps parsing useful in environments where those tools are absent and keeps ordinary generation from silently launching them.

Language services consume a projection

A programming-language server expects ordinary source files arranged for a compiler. The author, however, edits fragments arranged for explanation. Literate bridges those two views by projecting the validated fragment graph into generated source in memory and retaining mappings for unchanged literal text.

The projection is not a write operation and not a shortcut around validation. Missing references, cycles, invalid output roots, or unsupported ambiguities can block the complete projection. Once projected, a host may ask another language tool for a hover, completion, definition, diagnostic, or edit, then conservatively map an accepted result back to the literate source.

This consumer demonstrates why the shared center is more important than sharing a single output type. Generation wants complete file contents. Publication wants a document model. Language intelligence wants source plus mappings. All three depend on one graph and one account of where its text came from.

Effects carry host-specific obligations

A semantic core can promise that a path is portable and remains beneath the project root. It cannot promise that the path on a particular filesystem is not a symbolic link, that an editor result is still current, or that an external process will terminate. Those obligations begin where pure values meet an environment.

Every host therefore owns four questions:

  1. Acquisition: Which exact texts and settings form this snapshot?
  2. Intent: Is the operation inspecting, comparing, rendering, projecting, or writing?
  3. Effect safety: What must be checked before touching files, editors, browsers, or processes?
  4. Reporting: How can a person or another tool distinguish success, rejection, cancellation, stale work, and partial cleanup?

The answers differ by environment, but they should be explicit. Hiding acquisition inside parsing or hiding writes inside preview makes a tool convenient only until something fails.

Shared meaning does not remove honest differences

The command line cannot see an unsaved editor buffer unless one is supplied as part of a complete snapshot. An editor filesystem provider may not expose the same permission details as a local filesystem. A browser preview and a print renderer have different layout capabilities. A language server may decline to map a result that crosses generated indentation or appears in several expansions.

These are boundary differences, not permission to disagree about the project. Literate aims for semantic agreement while reporting environmental limitations plainly.
