Literate Programming

Literate programming is a programming paradigm introduced by Donald Knuth. A program is written in a natural language with snippets of code interspersed. From this text usable source code is generated, along with well formatted human-readable document.

The most important influence for this literate programming extension is the PBR Book.

This extension provides a set of tools that help the programmer writing literate programs. Through automation the process of writing literate programs should be as painless as possible. The programmer writes his literate programs using Markdown. When a literate programmer needs a snippet they can add a code fence. In this extension snippets are called code fragments. Building on the framework provided by Visual Studio Code this extension introduces code completion, code actions, definition provider, hover tooltips and a fragment explorer.

The approach for this extension is based on Markdown documents. For this extension the Markdown specification is only slightly adapted to make supporting literate programming easy. The code fragments are expressed in code fences as per the Markdown specification, either with surrounding triple backticks or triple tildes. Along with the programming language identifier the opening line has been extended to contain the fragment name and type essentially as options to the code fence. The opening line thus will look like py : <<fragment name>> to create a new fragment, or like py : <<fragment name>>=+ to amend an existing fragment.

The order of declaration of code fragments does not matter. It is possible to reference code fragments before they are created. It is thus possible to write fragments that reference code fragments that haven't been seen yet. The only requirement is that code fragments referenced by other code fragments eventually are created.

From fragment to source code

Fragments themselves don't directly create source files in most cases, but in the end source files is what is wanted from this extension.

To create actual source files a fragment creation line needs to be used with a slightly extended form of the creation tag mentioned above. The name has to be suffixed with the string .* between the chevrons. Furthermore a file name needs to be specified after the equal sign which is followed by whitespace and a dollar sign $. This is essentially a relative path that is going to be appended to each workspace folder as the root. A top-level fragment looks like py : <<top-level fragment.*>> = ./src/source.py $. The name of this fragment is top-level fragment, and once it has been fully extrapolated will it be written to a file in the workspace folder under src as the file source.py.

The Literate Programming extension allows the program author to write multiple projects in the same Visual Studio Code workspace. Each workspace folder is the root for its own literate project. Within each project there can be one or more literate files. These files carry the extension .literate. One literate file can contain zero or more code fragments. A literate file can also contain more than one top level fragment. In other words an author can create multiple source files within just one literate document.

This text describes the Literate Programming extension as a literate program.

Two ways to generate the same program

The editor and CLI are adapters around one engine. They differ in where they read text and how they report results, not in the fragment language they accept. The editor's Markdown preview is a separate presentation path: it does not write source files or the generated book.

Fragment Model

The tools provided by the Literate Programming extension are built around one repository of the project providing all necessary information around fragments.

The fragment repository handles parsing of literate documents, reacting to changes made by users. The repository provides all fragments found in the projects added to the current workspace. Additionally the repository will write out source files and rendered HTML files.

The fragment model is defined in the FragmentRepository class, which will be described in detail after introducing a couple of classes that help the repository.

Each workspace URI identifies a separate set of state. private isWatchedInput(uri: vscode.Uri, folder: vscode.WorkspaceFolder): boolean {
  if (this.generatedOutputs.get(folder.uri.toString())?.has(uri.toString())) { return false; }
  const relative = path.posix.relative(folder.uri.path, uri.path);
  if (relative.split('/').slice(0, -1).some(part => discoveryExcludedDirectories.includes(part))) {
    return false;
  }
  if (relative.endsWith('.literate')) { return true; }
  const documents = new Map((this.sourceDocuments.get(folder.uri.toString()) || [])
    .map(document => [document.path, document]));
  for (const document of vscode.workspace.textDocuments) {
    if (!document.isClosed && document.uri.path.endsWith('.literate')
      && vscode.workspace.getWorkspaceFolder(document.uri)?.uri.toString() === folder.uri.toString()) {
      const name = path.posix.relative(folder.uri.path, document.uri.path);
      if (!name.split('/').slice(0, -1).some(part => discoveryExcludedDirectories.includes(part))) {
        documents.set(name, { path: name, text: document.getText() });
      }
    }
  }
  for (const document of documents.values()) {
    try {
      if (templateReferences([document]).includes(relative)) { return true; }
    } catch (_) {}
  }
  return false;
}

Subscribing to text document changes

Processing literate files

The extension is an I/O adapter for the same pure generateProject engine used by the CLI. It snapshots every discovered document, preferring open editor buffers (including empty unsaved buffers), and loads the templates requested by templateReferences. Paths returned by that helper have already been checked by the engine. Missing template files are omitted so the engine can report the error at the declaration, rather than hiding it behind a filesystem exception. Other I/O failures reject the operation and are reported to the user. If template discovery rejects an invalid declaration, generation still runs to diagnose it at its source location. If document ordering rejects invalid input, the engine has already diagnosed it and the navigation parser does not parse it again.

processLiterateFiles defaults to a read-only refresh for completion providers. Activation, content changes and the Process command explicitly request writes. All requests share a serial queue: parsing and writing cannot overlap, and a failed request does not poison later requests. The returned promise covers the whole operation, including directory creation and file writes. Generated source and HTML changes do not themselves trigger processing.

The engine owns validation, expansion, settings, templates and HTML generation. Its zero-based diagnostic positions map directly to VS Code ranges. Diagnostics are replaced only for the workspace being processed, preserving other folders. An invalid project produces no writes; existing outputs remain untouched. For a valid project the adapter compares UTF-8 bytes with disk, creates parent directories, and awaits writes only for changed files. This avoids unnecessary watcher events and preserves the engine's identical output across platforms. Changed outputs are staged as a batch, installed by rename, and rolled back on caught failures. Originals stay available until commit; failed recovery reports retained backup locations. This is not crash-durable or simultaneously visible across all files. Obsolete outputs are not deleted.

The navigation map is deliberately unexpanded and is built from the same snapshot, ordered by the engine's orderSourceDocuments: root index first, linked chapters next, and every remaining document in deterministic order. This map is not another generator and never supplies generation diagnostics.

A content-change request follows this sequence. Navigation providers use the same refresh path but omit the output-writing branch. The serial queue keeps a second request waiting until the first has finished, including its writes.

Processing refreshes the cached theme alongside the document snapshot. A changed selection requests a preview refresh without waiting on rendering, so the serial processing queue cannot deadlock with a preview request.

<<fragment generation method>>=+ 
processLiterateFiles(
  trigger : vscode.WorkspaceFolder | vscode.TextDocument | undefined,
  writeFiles = false
) : Promise<void> {
  const operation = this.processingQueue.then(async () => {
    if (this.disposed) { return; }
    const folder = trigger && ("eol" in trigger
      ? determineWorkspaceFolder(trigger) : trigger);
    const folders = trigger ? (folder ? [folder] : [])
      : vscode.workspace.workspaceFolders || [];
    for (const workspaceFolder of folders) {
      const documents: SourceDocument[] = [];
      for (const uri of await getLiterateFileUris(workspaceFolder)) {
        documents.push({
          path: path.posix.relative(workspaceFolder.uri.path, uri.path),
          text: await getFileContent(uri)
        });
      }
      const themeKey = workspaceFolder.uri.toString();
      const theme = previewThemeName(documents);
      const previousTheme = this.previewThemes.get(themeKey) ?? defaultThemeName;
      this.previewThemes.set(themeKey, theme);
      if (theme !== previousTheme) {
        void vscode.commands.executeCommand('markdown.preview.refresh').then(undefined, () => undefined);
      }
      const templates: Record<string, string> = Object.create(null);
      let references: string[] = [];
      try {
        references = templateReferences(documents);
      } catch (_) {}
      for (const reference of references) {
        try {
          templates[reference] = await getFileContent(
            vscode.Uri.joinPath(workspaceFolder.uri, reference));
        } catch (error) {
          if (!(error instanceof vscode.FileSystemError) || error.code !== 'FileNotFound') {
            throw error;
          }
        }
      }
      const result = generateProject(documents, templates);
      const diagnostics = new Map<string, vscode.Diagnostic[]>();
      for (const diagnostic of result.diagnostics) {
        const uri = vscode.Uri.joinPath(workspaceFolder.uri, diagnostic.path);
        const key = uri.toString();
        const entries = diagnostics.get(key) || [];
        const range = new vscode.Range(diagnostic.line, diagnostic.column,
          diagnostic.line, diagnostic.column + 1);
        const entry = new vscode.Diagnostic(range, diagnostic.message,
          vscode.DiagnosticSeverity.Error);
        if (diagnostic.code !== undefined) { entry.code = diagnostic.code; }
        entries.push(entry);
        diagnostics.set(key, entries);
      }
      const stale: vscode.Uri[] = [];
      this.diagnostics.forEach(uri => {
        if (vscode.workspace.getWorkspaceFolder(uri)?.uri.toString() === workspaceFolder.uri.toString()) {
          stale.push(uri);
        }
      });
      for (const uri of stale) { this.diagnostics.delete(uri); }
      for (const [uri, entries] of diagnostics) {
        this.diagnostics.set(vscode.Uri.parse(uri), entries);
      }
      const states = new GrabbedStateList();
      const fragments = new FragmentMap();
      const key = workspaceFolder.uri.toString();
      this.grabbedStateForWorkspaceFolders.set(key, states);
      this.fragmentsForWorkspaceFolders.set(key, fragments);
      this.sourceDocuments.set(key, []);
      this.occurrences.set(key, []);
      let ordered: SourceDocument[];
      try {
        ordered = orderSourceDocuments(documents);
                this.occurrences.set(key, collectFragmentOccurrences(ordered));
                this.sourceDocuments.set(key, ordered);
      } catch (_) {
        continue;
      }
      for (const document of ordered) {
        const env: GrabbedState = {
          literateFileName: document.path,
          literateUri: vscode.Uri.joinPath(workspaceFolder.uri, document.path),
          gstate: new StateCore('', this.md, {})
        };
        this.md.parse(document.text, env);
        states.list.push(env);
      }
      fragments.map = handleFragments(states.list, result.inspection.fragments);
      if (!writeFiles || result.diagnostics.length) { continue; }
      this.generatedOutputs.set(key, new Set(result.files.map(file =>
        vscode.Uri.joinPath(workspaceFolder.uri, file.path).toString())));
      const outputs = await this.preflightOutputs(workspaceFolder.uri, result.files);
      await this.writeChangedOutputs(outputs);
    }
  });
  this.processingQueue = operation.catch(error => {
    void vscode.window.showErrorMessage(`Literate processing failed: ${String(error)}`);
  });
  return operation;
}

Preflighting output paths

Before reading any output contents, preflight every source and HTML output in this project. The shared safeRelativePath policy keeps paths beneath the trusted workspace root; only components below that boundary are inspected. Filesystem access stays in workspace.fs, including for remote workspace URIs.

Check the symbolic-link bit before checking the exact expected type: providers can combine SymbolicLink with File or Directory. Unknown and special types are not safe substitutes. A missing component ends the walk, since descendants cannot exist beneath it. However, stat may follow a dangling link and report FileNotFound. In that case inspect the already-checked parent's directory entries before treating the component as absent. Other errors must propagate.

<<fragment generation method>>=+ 
private async preflightOutputs(
  root: vscode.Uri, files: readonly { path: string; content: string }[]
): Promise<{ files: TransactionFile[]; io: TransactionIO }> {
  const io = this.outputTransactionIO(root);
  const outputs: TransactionFile[] = [];
  for (const file of files) {
    if (await io.inspect(file.path) === 'directory') {
      throw new Error(`Unsafe output path (expected file): ${file.path}`);
    }
    outputs.push({ path: file.path, content: Buffer.from(file.content, 'utf-8') });
  }
  return { files: outputs, io };
}

The filesystem adapter supplies the transaction's small I/O contract. It keeps URIs intact for remote providers and validates every relative path before use. Generated destinations are registered before staging or committing can emit input-shaped watcher events.

<<fragment generation method>>=+ 
private outputTransactionIO(root: vscode.Uri): TransactionIO {
  const modes = new Map<string, number>();
  const uriFor = (relative: string): vscode.Uri => {
    const safe = safeRelativePath(relative);
    if (!safe) { throw new Error(`Unsafe output path: ${relative}`); }
    return vscode.Uri.joinPath(root, safe);
  };
  const inspect: TransactionIO['inspect'] = async relativePath => {
    const relative = safeRelativePath(relativePath);
    if (!relative) { throw new Error(`Unsafe output path: ${relativePath}`); }
    const parts = relative.split('/');
    let parent = root;
    for (let index = 0; index < parts.length; index++) {
      const uri = vscode.Uri.joinPath(parent, parts[index]);
      const type = await this.outputEntryType(parent, uri, parts[index]);
      if (type === undefined) { return 'missing'; }
      if (type & vscode.FileType.SymbolicLink) {
        throw new Error(`Unsafe output path (symbolic link): ${uri.toString()}`);
      }
      const leaf = index === parts.length - 1;
      if (type !== vscode.FileType.Directory && !(leaf && type === vscode.FileType.File)) {
        throw new Error(`Unsafe output path (expected ${leaf ? 'file or directory' : 'directory'}): ${uri.toString()}`);
      }
      if (leaf) { return type === vscode.FileType.File ? 'file' : 'directory'; }
      parent = uri;
    }
    throw new Error(`Unsafe output path: ${relativePath}`);
  };
  const requireType = async (relative: string, expected: 'missing' | 'file' | 'directory'): Promise<void> => {
    if (await inspect(relative) !== expected) {
      throw new Error(`Unsafe output path (expected ${expected}): ${relative}`);
    }
  };
  const requireParent = async (relative: string): Promise<void> => {
    const safe = safeRelativePath(relative);
    if (!safe) { throw new Error(`Unsafe output path: ${relative}`); }
    const parent = safe.split('/').slice(0, -1).join('/');
    if (parent) { await requireType(parent, 'directory'); }
    else { await vscode.workspace.fs.readDirectory(root); }
  };
  const removeDirectory = async (relative: string): Promise<void> => {
    await requireType(relative, 'directory');
    const uri = uriFor(relative);
    if ((await vscode.workspace.fs.readDirectory(uri)).length) {
      throw new Error(`Output directory is not empty: ${relative}`);
    }
    await vscode.workspace.fs.delete(uri, { recursive: false, useTrash: false });
  };
  return {
    inspect,
    read: async relative => {
      await requireType(relative, 'file');
      const uri = uriFor(relative);
      if (uri.scheme === 'file') {
        const stat = await lstat(uri.fsPath);
        if (stat.isSymbolicLink() || !stat.isFile()) {
          throw new Error(`Unsafe output path (expected file): ${uri.toString()}`);
        }
        modes.set(uri.toString(), stat.mode & 0o7777);
      }
      return vscode.workspace.fs.readFile(uri);
    },
    mkdir: async relative => {
      await requireType(relative, 'missing');
      await requireParent(relative);
      try { await vscode.workspace.fs.createDirectory(uriFor(relative)); }
      catch (error) {
        let createdEmptyDirectory = false;
        try {
          if (await inspect(relative) === 'directory') {
            if ((await vscode.workspace.fs.readDirectory(uriFor(relative))).length) {
              throw new Error(`Output directory is not empty: ${relative}`);
            }
            createdEmptyDirectory = true;
            await removeDirectory(relative);
          }
        } catch (cleanupError) {
          const message = `Directory creation failed: ${relative}; ${String(error)}; empty-directory cleanup failed: ${String(cleanupError)}`;
          if (createdEmptyDirectory) { throw new TransactionDirectoryError(relative, message); }
          throw new Error(message);
        }
        throw error;
      }
    },
    writeNew: async (relative, content) => {
      await requireType(relative, 'missing');
      await requireParent(relative);
      await vscode.workspace.fs.writeFile(uriFor(relative), content);
    },
    rename: async (from, to) => {
      await requireType(from, 'file');
      await requireType(to, 'missing');
      await requireParent(to);
      const source = uriFor(from), target = uriFor(to);
      const mode = modes.get(target.toString());
      if (source.scheme === 'file' && from.endsWith('.stage') && mode !== undefined) {
        await chmod(source.fsPath, mode);
      }
      await vscode.workspace.fs.rename(source, target, { overwrite: false });
    },
    removeFile: async relative => {
      await requireType(relative, 'file');
      await vscode.workspace.fs.delete(uriFor(relative), { recursive: false, useTrash: false });
    },
    removeDirectory,
    nonce: randomUUID
  };
}

The entry lookup distinguishes an absent path from a dangling link. Only a FileNotFound response permits the directory-entry fallback; permission and provider failures must stop generation rather than authorize a write.

<<fragment generation method>>=+ 
private async outputEntryType(parent: vscode.Uri, uri: vscode.Uri, name: string): Promise<vscode.FileType | undefined> {
  try {
    return (await vscode.workspace.fs.stat(uri)).type;
  } catch (error) {
    if (!(error instanceof vscode.FileSystemError) || error.code !== 'FileNotFound') {
      throw error;
    }
  }
  const entries = await vscode.workspace.fs.readDirectory(parent);
  return entries.find(([entry]) => entry === name)?.[1];
}

These checks depend on the provider reporting links through stat or directory entries. VS Code has no portable no-follow open/write API: concurrent filesystem changes can race the checks (TOCTOU). VS Code also has no exclusive mkdir or exclusive writeFile operation. The adapter checks absence and the immediate parent before creation, assuming no concurrent external changes. If directory creation throws after taking effect, it attempts to remove the empty directory. If a confirmed empty created directory cannot be removed, TransactionDirectoryError transfers ownership to the coordinator for rollback cleanup; persistent failure reports that artifact's recovery path along with the creation and cleanup errors. The workspace URI is the trusted boundary (not statted); directory listing checks that boundary when checking a missing immediate child or creating beneath it. Providers must honor non-overwriting move semantics and nonrecursive deletion. This is recoverable exception handling, not a security sandbox, crash-durable journal, or simultaneous atomic visibility across outputs. Rollback failures preserve recovery locations and propagate the transaction error. Read-only navigation refreshes bypass both output preflight and output writes.

Writing changed outputs

Only after the entire project's preflight succeeds does the shared coordinator compare disk bytes, stage every changed file, and install the batch by rename. Open output buffers are not used for this comparison. Each workspace remains a separate transaction. Numbered stage and backup names do not end in .literate, so their watcher events do not trigger input processing.

For local file URIs, reading an existing output snapshots its POSIX permission bits with Node lstat; chmod applies those bits to the stage before installation. Rollback moves the original backup back without changing its mode. New outputs use provider defaults. Remote URIs use only workspace.fs, which exposes no mode API: replacement metadata follows provider defaults, and remote permission or metadata restoration is not guaranteed. Ownership, ACLs and other metadata are not preserved by this local permission-bit handling either.

Fragment structure and regular expressions

Before we dive deeper into the processing of .literate documents it is necessary to have a look at how fragments work.

Fragments in the literate extension have a specific format that requires a bit of explaining.

There are four types of fragment tags, three of which either create or modify a fragment, and one that expresses fragment usage.

Generation, preview and editor commands use the shared engine header grammar and tag scanner. Only accepted declarations receive fragment decoration.

Gathering editor fragments

The engine inspection identifies accepted definitions in deterministic order. We attach the corresponding Markdown tokens for existing editor commands without parsing declarations a second time. Unrelated generation errors need not prevent navigation or a valid rename.

<<handle fragments>>= 
function handleFragments(
  envList: GrabbedState[], inspected: FragmentInspection[]
): Map<string, FragmentInformation> {
  const fragments = new Map<string, FragmentInformation>();
  for (const entry of inspected) {
    const parts = entry.definitions.flatMap(definition => {
      const env = envList.find(item => item.literateFileName === definition.path);
      const token = env?.gstate.tokens.find(item =>
        item.type === 'fence' && item.map?.[0] === definition.line);
      return env && token ? [{ env, token }] : [];
    });
    if (!parts.length) { continue; }
    const env = parts[0].env;
    fragments.set(entry.name, {
      lang: entry.language, literateFileName: env.literateFileName,
      sourceFileName: entry.output || '', templateFileName: undefined,
      code: parts.map(part => part.token.content).join(''),
      tokens: parts.map(part => part.token), env
    });
  }
  return fragments;
}

custom code fence rendering

Our extension uses a custom code fence rendering rule for the live Markdown preview to ensure the code fragment name is also rendered as part of the fence. The generated book uses the engine renderer instead.

Each installation captures the parser's existing fence rule, never a shared mutable renderer. Configuration fences stay hidden. Plain fences whose trimmed info is exactly mermaid bypass highlighting and expose escaped, original source to the bundled browser client through pre.literate-mermaid. The wrapper selects the owning workspace's root index theme, preferring an open buffer over the repository snapshot. Repository processing caches the effective theme through workspace.fs, so remote workspaces need no synchronous filesystem fallback. Protecting fragment tags

With protectFragmentTags we can adjust the rendered HTML as received from the original fence rule. We'll search for HTML that is our fragment tag: &lt;&lt, followed by tag name, followed by &gt;&gt;. Such occurrances we wrap in a span tag that has the CSS class clean-literate-tag-name. The class can be set up to essentially override any styling applied through hljs-keyword.

For matching we use two regular expressions, FRAGMENT_HTML_RE and FRAGMENT_HTML_KEYWORD_CLEANUP_RE.

With FRAGMENT_HTML_KEYWORD_CLEANUP_RE all span tags injected by hljs can be cleaned up, and with FRAGMENT_HTML_RE we can wrap our fragment tag names in a class of our own, literate-name-tag to handle special styling for tags in code fences.

<<fragment regular expressions>>= 
const FRAGMENT_HTML_CLEANUP_RE= /(<span.class="hljs-.+?">)(.*?)(<\/span>)/g;
const FRAGMENT_HTML_RE= /(&lt;&lt;.+?&gt;&gt;)/g;

Since these regular expressions are used with replaceAll they need to be marked global with g.

To make sure the highlights are properly cleaned we introduce an inline function cleanHighlights that takes care of all the highlights by using a replaceAll on the match passed on to cleanHighlights. The result is used to wrap inside the span with the literate-name-tag class.

<<fragment tag protector>>= 
function protectFragmentTags(rendered : string) : string {
  function cleanHighlights(match : string, _: number, __: string)
  {
    let internal = match.replaceAll(FRAGMENT_HTML_CLEANUP_RE, "$2");
    return `<span class="literate-tag-name">${internal}</span>`;
  }
  return rendered
    .replaceAll(
      FRAGMENT_HTML_RE,
      cleanHighlights
    );
}

In our CSS file we can now specify .literate-tag-name to say an italic font to stand out in the code fences.

Remove code comments

In rendered HTML code comments are wrapped in span tags with the class hljs-comment. These can be on one line, or for comment blocks on multiple lines. Since the goal is to remove these completely from rendered HTML the regular expression for the match will be just to do that: match the span with the hljs-comment even if it is over several lines. To do that we use also the s modifier to the expression.

Diagnostics

Generation diagnostics come exclusively from the engine, including malformed headers, missing templates, invalid output paths, missing fragments and cycles. The adapter preserves their zero-based line and column coordinates, grouping errors by full document URI in the Problems panel. Navigation helpers do not emit a second, potentially contradictory set of validation errors.

Utility functions

Discovering inputs and reading buffers

Discovery includes all .literate files, not just index-linked chapters. Passing null as the exclusion argument avoids silently dropping files through editor search exclusions. Both discovered URIs and open buffers are filtered using the engine's shared discoveryExcludedDirectories, matching CLI discovery. Exact directory components relative to the workspace root are checked at every depth: node_modules, out, dist, .git, .yarn, and .vscode-test are excluded. Similar names and filenames are not excluded. Open workspace documents are merged by full URI so new, not-yet-saved file-backed documents participate too. Untitled documents have no workspace-relative output location and are not included. Discovery sorts full URIs; the engine applies the semantic chapter ordering after contents are read.

The buffer lookup uses full URI equality, not relative names that can collide between workspace folders. Presence, rather than truthiness of the text, decides whether to read from disk: an empty buffer must stay empty. This same lookup applies to templates, so unsaved template edits are used on the next processing request. Automatic processing watches literate content changes only; use Process after changing a template without changing a literate document.

<<utility functions>>= 
async function getLiterateFileUris(workspaceFolder: vscode.WorkspaceFolder): Promise<vscode.Uri[]> {
  const uris = new Map<string, vscode.Uri>();
  const excluded = new Set<string>(discoveryExcludedDirectories);
  const included = (uri: vscode.Uri): boolean => !path.posix
    .relative(workspaceFolder.uri.path, uri.path).split('/').slice(0, -1)
    .some(directory => excluded.has(directory));
  const pattern = new vscode.RelativePattern(workspaceFolder, '**/*.literate');
  for (const uri of await vscode.workspace.findFiles(pattern, null)) {
    if (included(uri)) { uris.set(uri.toString(), uri); }
  }
  for (const document of vscode.workspace.textDocuments) {
    if (document.uri.path.endsWith('.literate') && included(document.uri) &&
        vscode.workspace.getWorkspaceFolder(document.uri)?.uri.toString() === workspaceFolder.uri.toString()) {
      uris.set(document.uri.toString(), document.uri);
    }
  }
  return Array.from(uris.keys()).sort().map(key => uris.get(key)!);
}

async function getFileContent(file: vscode.Uri): Promise<string> {
  const document = vscode.workspace.textDocuments.find(
    document => document.uri.toString() === file.toString());
  if (document !== undefined) { return document.getText(); }
  return new TextDecoder('utf-8').decode(await vscode.workspace.fs.readFile(file));
}
